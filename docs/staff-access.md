# Staff accounts and module access

Staff register at `/admin/signup` using an exact `navawilson.law` or `iclosed.ca` email domain. Existing accounts use the same login; this does not create a separate identity store. Supabase must keep email confirmation enabled. Eligibility is enforced again on the server, so an arbitrary email submitted directly to the shared customer-auth endpoint never grants staff access.

The verified `saru@navawilson.law` account is the owner. `/admin/access` and `/api/admin/access` are owner-only. The owner grants module IDs and can disable portal access. New accounts and new staff invitations have no modules by default. Existing legacy admins retain modules until explicitly scoped. Staff profiles and module grants are separate: a Clerk/Lawyer/Admin display label cannot grant permissions. The owner cannot be disabled or reassigned through these screens.

`app_metadata.staff_modules` and `app_metadata.staff_disabled` are server-owned claims, updated only through the owner API. Never use editable `user_metadata` for authorization. Existing unrelated metadata is preserved. Changes record the actor/time in metadata and use the existing best-effort audit logger. The existing auth account, password and customer records are preserved. No database migration is required.

Middleware revalidates `getUser()` and enforces module access on pages and APIs. The sidebar hides unavailable modules; the API gate remains authoritative even if a stale browser menu is visible. Users can refresh the page after grants to update the menu. AuthProvider loads the latest verified user record on page load/navigation and revalidates after authentication events; cached token metadata cannot overwrite that record. Unknown routes and administrative maintenance endpoints are owner-only. Existing explicitly public customer/service endpoints retain their current independent authentication.

These are module permissions, not per-file, per-field or read/write permissions. All Files and Tasks share supporting file record reads; Dashboard and Search do not independently grant access to those APIs. Record writes require the owning operational module. Supporting template/calendar reads are shared with the forms that need them. The public calculator remains public. Database RLS/customer-portal permissions are unchanged and must be assessed separately for database-wide isolation. Future module routes must be added to the central policy with tests; unclassified APIs fail closed to owner-only.

## Deployment and acceptance

Keep Supabase signup enabled and email auto-confirm disabled. These were checked read-only during development. Add each deployed origin's `/admin/auth/confirm` URL to Supabase Authentication URL Configuration Redirect URLs, preserving existing customer callbacks. For dev use `https://devadmin.iclosed.ca/admin/auth/confirm`; localhost preview uses `http://127.0.0.1:3004/admin/auth/confirm`. Do not replace the shared Site URL or alter customer email templates as routine setup.

The callback exchanges a PKCE code and only redirects within the same origin. The verification email should be opened in the browser used to register. Confirmation callbacks are omitted from Next incoming request logs. Live delivery, redirect allowlist, and end-to-end email acceptance need verification before rollout; no real signup emails or permission updates were sent during automated tests.

Acceptance: register a controlled company test address, verify email, confirm no tabs and denied direct API access; use Saru's User Access page to grant Finance only; refresh the staff page without signing out and confirm Finance appears while Legal Assistant and User Access are blocked; revoke Finance and verify subsequent API calls are denied. Test account creation and grant changes require a controlled test account because the Supabase project is shared with the customer portal.

## Google sign-in

Login and signup offer Google OAuth through a server-initiated PKCE flow at `/admin/auth/google` and the existing cookie-backed callback at `/admin/auth/confirm`. Email/password remains available. The callback revalidates the user with `getUser()` and applies the same `canSignIn` and `homePath` policy; Google identity/profile metadata never grants modules. Disallowed or disabled identities are signed out. A new verified company account lands on `/admin/welcome` with no modules. Existing verified-email identity linking is handled by Supabase, preserving the account's server-owned grants; do not create replacement staff records or enable manual account linking as part of setup.

Configure a dedicated Web OAuth client in the iClosed Google Cloud project, with the dev Supabase callback `https://awygszzpyotaddnspikt.supabase.co/auth/v1/callback` as an exact authorized redirect URI. Store its client ID and secret only in the **dev** Supabase Google provider settings. Keep nonce verification on and allow-users-without-email off. The server requests only `openid email profile`; it does not request Drive, Gmail or offline access. Leave the existing audit mailbox client, customer callbacks, Site URL and production configuration unchanged. The provider is shared at the Supabase project level, so enforce staff eligibility at Admin's server gate rather than globally blocking customer signup domains.

Acceptance on hosted dev: test the Google round trip with an existing verified staff account (same account ID/grants), a new controlled company account (no tabs), a non-company account (denied Admin access), cancellation and a disabled account. The policy regression suite covers both company domains, spoofed Google profile claims, owner identity, disabled/unverified users and existing grants. Live Google acceptance still requires account-owner interaction; do not claim it from unit tests alone.
