1. Executive Summary

The iClosed Admin Portal is a Next.js 16 (App Router) application supporting a Canadian real-estate transaction workflow: lead intake → conversion → deal management → tasks/milestones → document collection → client communication. The platform integrates Supabase (auth + Postgres), Vercel Blob (file storage), Resend (transactional email), and Google Gemini (AI document identification).

The product is functionally rich and largely feature-complete for its target use case, with sophisticated family-deal logic (co-purchasers/co-sellers) and a comprehensive intake workflow. However, the review has surfaced a meaningful number of security, compliance, and reliability gaps that should be addressed before the product is scaled beyond a pilot deployment — particularly given the sensitive PII it handles (government-issued IDs, addresses, contact details, transaction documents).

Top 5 must-fix items

  1. SEC-001 — Admin API routes accept requests without verifying the caller is authenticated or holds the admin role. Any actor who knows a route URL can read or mutate data.
  2. SEC-002 — Public webhook endpoints have no signature verification. Anyone can trigger deal activation or welcome-email blasts.
  3. SEC-003 / CMP-001 — Government identification documents are uploaded to Vercel Blob with access: "public". URL guessability is the only control — a PIPEDA red flag.
  4. CMP-002 — The intake flow collects extensive PII without an explicit consent checkpoint (no privacy-policy acknowledgement, no stored consent timestamp).
  5. CMP-003 — Government IDs are forwarded to Google Gemini for classification with no documented sub-processor disclosure or data-processing addendum.
Overall posture. The platform is functionally feature-rich but requires security and compliance hardening before broad rollout. With ~2–4 weeks of focused remediation on the P0 items in §9, the platform can reach a defensible production baseline. The longer-tail items (§9 P1 and P2) bring it to a robust, audit-ready state. The database review in §7 surfaces two additional Critical items — DB-001 (duplicate production tables) and DB-002 (type-broken updated_at) — that should also be addressed in P0.

4. Security Findings

4.1 Critical

SEC-001 — Admin API routes accept requests without authentication or role check Critical

Location: src/app/api/admin/leads/route.ts:40-51, src/app/api/admin/deals/route.ts, src/app/api/admin/convert-lead/route.ts:18, src/app/api/admin/task-responses-batch/route.ts, and ~20 sibling routes under src/app/api/admin/*.
Description. The vast majority of admin-facing API routes execute supabaseAdmin (service-role) queries without first verifying that the request carries a valid Supabase session or that the session belongs to a user with the admin role. A small subset (e.g. account/update-email) does extract and verify a Bearer token; this pattern is not generalised.
Impact. An unauthenticated attacker who discovers a route URL can list, create, update, or delete leads, deals, tasks, documents, and email templates. They can convert leads, send emails to clients on behalf of the platform, or impersonate any customer.
Recommendation. (1) Add src/middleware.ts gating /admin/** and /api/admin/**, verifying a Supabase session cookie or Authorization: Bearer header and app_metadata.role === "admin". (2) Provide a reusable requireAdmin(req): Promise<User> helper in src/lib/ and call it at the top of every admin route. (3) Add an integration test that asserts unauthenticated fetch against each /api/admin/* endpoint returns 401.

SEC-002 — Public webhook endpoints accept payloads without signature verification Critical

Location: src/app/api/webhooks/new-lead/route.ts, src/app/api/webhooks/activate-deal/route.ts
Description. Both webhook endpoints accept arbitrary JSON bodies ({ email, lead_id, client_id }) and immediately mutate state — sending welcome emails or activating deals — with no HMAC signature, shared-secret header, or IP allow-list.
Impact. Anyone with the public URL can (a) enumerate or harvest lead emails by triggering welcome-email blasts, (b) prematurely activate deals, or (c) cause spurious billing / email-cost spikes.
Recommendation. Adopt HMAC-SHA-256. Calling system signs the raw body with WEBHOOK_SHARED_SECRET; the route extracts X-iClosed-Signature and validates via crypto.timingSafeEqual. Reject mismatches with 401.

SEC-003 — Identification and APS documents stored on public Vercel Blob Critical

Location: src/app/api/admin/uploadblobstorage/route.ts:31-38 (also tracked as compliance issue CMP-001)
Evidence:
const blob = await put(
  `corporate-docs/${lead_id}/${Date.now()}-${file.name}`,
  file,
  { access: "public", ... }
);
Description. access: "public" makes every uploaded driver's licence, passport, SIN card, or APS publicly readable by URL. Security relies entirely on URL guessability — there is no token, expiry, or access check on the file itself.
Impact. A single leaked URL (browser history, email, screenshot, log file, referrer header) exposes the underlying document indefinitely. For Canadian client data this is also a PIPEDA exposure.
Recommendation. Switch all PII uploads to access: "private" (or token). Add a server-side proxy route GET /api/admin/documents/[id]/download that performs auth + access check, then streams the blob via short-TTL signed URL. Migrate existing public blobs.

4.2 High

SEC-004 — IDOR on deal PATCH; no ownership check High

Location: src/app/api/admin/deals/[id]/route.ts:349-468
Description. Once SEC-001 is fixed, any authenticated admin can still PATCH any deal by ID; there is no row-level check that the actor should have access to the targeted deal.
Recommendation. Add per-deal access control. Document the "all admins can edit all deals" assumption explicitly in the short term. Medium-term: enable Supabase RLS as defence in depth.

SEC-005 — Blob URL allow-list uses bypassable endsWith check High

Location: src/app/api/admin/deals/[id]/uploadblobstorage/route.ts:62-76
Description. Validates fileUrl by endsWith(".public.blob.vercel-storage.com") against a string. Crafted URLs (https://attacker.com/path?x=foo.public.blob.vercel-storage.com or basic-auth-style misuse) can defeat this.
Recommendation. Parse via new URL() and check url.hostname.endsWith(".public.blob.vercel-storage.com"). Better: issue an upload token (already wired in token/route.ts) that encodes deal_id and reconcile the blob path server-side.

SEC-006 — Impersonation route has no audit log and no second-factor gate High

Location: src/app/api/admin/impersonate/route.ts:39-57
Description. Any admin can mint a magic-link for any customer via auth.admin.generateLink. There is no record of who initiated impersonation, when, or why; no notification; no step-up authentication.
Recommendation. Write an audit_logs row; email the impersonated user; require fresh password / 2FA before issuing the link.

SEC-007 — Password-reset endpoint has no rate limit High

Location: src/app/api/admin/reset-password/route.ts
Description. Endpoint correctly returns a generic success message (prevents enumeration), but does not throttle. A trivial loop spams inboxes or burns Resend quota.
Recommendation. In-memory or Redis-backed limiter keyed by email and IP (5/hr per email, 30/hr per IP). Reject with the same generic success response.

SEC-008 — Invitation token reusable for up to 7 days High

Location: src/lib/invitationToken.ts:76-89
Description. Single-use is intentionally disabled to tolerate email-scanner pre-fetches. The trade-off is reasonable, but no upper bound on consumption count. A leaked token can be replayed multiple times.
Recommendation. Track consumption_count and refuse after e.g. 5 uses. Log each consumption with IP + UA. Consider 24-72h TTL for high-sensitivity invitations.

SEC-009 — Email template placeholder substitution allows reflective injection High

Location: src/lib/sendAuthEmail.ts:264-382, src/lib/sendWelcomeEmail.ts:103-186
Description. Templates rendered via successive String.replaceAll on {{ var.name }} tokens. If a user-controlled field (e.g. lead.notes) contains a placeholder string, subsequent passes will recursively substitute it. Fallback regex covers only auth-link patterns.
Recommendation. Use a proper templating engine (Handlebars / Nunjucks) with sandboxed context. At minimum, perform a single pass over a precompiled token list. HTML-escape every interpolated value.

SEC-010 — No security headers (CSP, HSTS, X-Frame-Options) High

Location: No src/middleware.ts; no header config in next.config.*
Recommendation. Set: Strict-Transport-Security: max-age=31536000; includeSubDomains; preload, X-Frame-Options: DENY, X-Content-Type-Options: nosniff, Referrer-Policy: strict-origin-when-cross-origin, a tailored CSP, and a restrictive Permissions-Policy.

SEC-011 — Gemini API key handled via raw env var with no per-user rate limit High

Location: src/services/geminiService.ts:10-14, src/app/api/admin/identify-document/route.ts:242-245
Recommendation. Rate-limit per actor (e.g. 30/hr); document rotation cadence; prefer OAuth/service-account credentials and IP allow-listing in Google Cloud Console.

5. Missing Logic & Functional Gaps

5.1 Data integrity & concurrency

GAP-001 — No optimistic concurrency on deal PATCH (last-write-wins) Medium

Location: src/app/api/admin/deals/[id]/route.ts:349-468
Description. When two admins open the same deal and save changes, the later request silently overwrites the first; neither user is informed of the conflict.
Recommendation. Require an expected_updated_at field. Compare to current updated_at inside the SQL update predicate; return 409 Conflict on mismatch with the latest snapshot.

GAP-002 — Race condition in family-deal lookup on rapid conversions Medium

Location: src/lib/convertLead.ts:39-43
Recommendation. Add a partial unique index in Postgres (UNIQUE (root_lead_id) WHERE deleted_at IS NULL) and handle constraint violation as "already exists; return existing row."

GAP-003 — Backfill endpoint has no idempotency guard Medium

Location: src/app/api/admin/backfill-shared-tasks/route.ts:36-41
Recommendation. Store a migration_runs row with a unique key per migration; refuse re-runs. Pair with authentication fix from SEC-001 / SEC-025.

GAP-004 — Shared-task mirror creates duplicate rows on retry Medium

Location: src/app/api/admin/task-responses/route.ts:621-636
Recommendation. Use UPSERT (ON CONFLICT (task_id, field_id, peer_lead_id) DO UPDATE) with the corresponding unique constraint.

GAP-005 — Deal delete leaves orphan tasks, milestones, and documents Medium

Location: src/app/api/admin/deals/[id]/route.ts:471-487
Recommendation. Declare ON DELETE CASCADE on FK constraints, or delete dependents in a single transaction prior to deal removal.

GAP-006 — Deal status transitions not validated Medium

Location: src/app/api/admin/deals/[id]/route.ts:313-317
Recommendation. Encode the state machine: Active ↔ Inactive; both → Closed (terminal). Reject invalid transitions with 400.

GAP-007 — Task status changes do not always trigger milestone recalc Medium

Location: src/app/api/admin/task-responses/route.ts:519-526
Recommendation. Centralise milestone recalculation behind a single helper called by every task-mutating endpoint, or add a Postgres trigger.

5.2 Upload & blob lifecycle

GAP-008 — Blob upload succeeds, DB insert fails → orphan bytes in Blob Medium

Location: src/app/api/admin/uploadblobstorage/route.ts:31-56
Recommendation. Wrap in try/catch and del() the blob on DB failure. Nightly reconciliation lists Blob keys and deletes any not referenced in the DB.

GAP-009 — No max file count, no file-size limit, no MIME allow-list Medium

Location: src/app/api/admin/uploadblobstorage/route.ts:31-56
Recommendation. Cap files at 25 MB; allow only image/jpeg, image/png, application/pdf, image/heic. Enforce per-task and per-deal upload counts.

GAP-010 — APS replacement deletes family-wide rows without scope Medium

Location: src/app/api/admin/deals/[id]/uploadblobstorage/route.ts:163-167
Recommendation. Scope the delete to (deal_id, doc_type, side) and run delete + insert in a single transaction.

5.3 Email & notification

GAP-011 — welcome_email_sent flag flipped after Resend call → duplicate sends possible Medium

Location: src/lib/sendWelcomeEmail.ts:351-358
Recommendation. Flip the flag in the same transaction that originated the send intent, or pass an Idempotency-Key to Resend.

GAP-012 — No retry on Resend transient failure Medium

Location: src/lib/sendWelcomeEmail.ts:337-347
Recommendation. 3-attempt exponential backoff; on final failure write a row to email_outbox for out-of-band retry.

GAP-013 — HTML-entity decoding in email body is incomplete Low

Location: src/lib/sendWelcomeEmail.ts:309-313
Recommendation. Use the html-entities package or a single regex covering the full entity table.

GAP-014 — Milestone-email fetch failures silently swallowed Medium

Location: src/lib/recalcMilestones.ts:135-155
Recommendation. Aggregate per-deal errors and return them in the response; log at WARN with deal IDs.

7. Database Schema Review

Findings below derive from the production public schema export shared on 2026-05-29. Prefix: DB-. Confirmation of these findings against live RLS policies, row counts, and existing indexes is pending Supabase dashboard access.

7.1 Critical

DB-001 — _duplicate tables present in the production schema Critical

Location: public.deals_duplicate, public.milestones_duplicate, public.tasks_duplicate
Description. Three near-identical copies of production tables live in the production database. Their column sets diverge subtly from the originals — e.g. deals_duplicate.status permits 'Cancelled' and 'Urgent', values the canonical deals.status CHECK rejects. Their RLS posture, indexes, and FK constraints are unknown without dashboard access.
Impact. (1) If these tables are reachable via PostgREST without RLS, they may leak data that the canonical tables protect. (2) Stale data inside them creates analytics confusion. (3) Future engineers will guess which table is authoritative; mis-routed writes will silently diverge from the canonical row.
Recommendation. Audit row counts and last-modified timestamps. If not in use, DROP TABLE. If still referenced anywhere, rename to archive_* and document. Run an unauthenticated probe against GET /rest/v1/deals_duplicate — if it returns rows, that's a data-leak incident requiring immediate notification.

DB-002 — email_templates.updated_at declared as text instead of timestamptz Critical

Evidence: updated_at text DEFAULT now()
Description. now() returns timestamptz but the column is text, so the default value is implicitly cast to a string at insert time. Any UPDATE that relies on date comparison, ordering, or filtering against this column will behave incorrectly (lexicographic vs chronological ordering will usually agree because ISO-8601 sorts alphabetically — but not reliably, and not for any range arithmetic).
Recommendation. Migrate the column type: ALTER TABLE email_templates ALTER COLUMN updated_at TYPE timestamptz USING updated_at::timestamptz;. Add a BEFORE UPDATE trigger to maintain it.

7.2 High

DB-003 — Foreign keys have no ON DELETE action — orphan rows or failed deletes High

Affected FKs: nearly every table — tasks.deal_id, milestones.deal_id, task_responses.task_id, lead_corporate_docs.lead_id, retainer_signatures.lead_id, deal_documents.deal_id, deal_notes.deal_id, deal_co_purchasers.deal_id, leads.parent_lead_id, etc.
Description. Postgres defaults FKs to NO ACTION when no behaviour is specified. Deleting a referenced parent row will fail. This is the root cause of GAP-005: the application's DELETE /api/admin/deals/[id] path can either error outright in production or, if a dev's local DB has different constraints, succeed and leave orphans.
Recommendation. Decide policy per relationship and declare it explicitly: ON DELETE CASCADE for owned children (task_responses follows tasks; milestones follow deals), ON DELETE RESTRICT for protected references (milestones.email_template_id), ON DELETE SET NULL where appropriate (deal_notes.created_by).

DB-004 — Missing indexes on FK columns and frequent lookup columns High

Likely-missing indexes: tasks.deal_id, tasks.milestone_id, tasks.task_template_id, milestones.deal_id, milestones.email_template_id, milestones.stage_template_id, task_responses.task_id, task_responses.field_id, lead_corporate_docs.lead_id, lead_identification_docs.lead_id, retainer_signatures.lead_id, deal_documents.deal_id, deal_co_purchasers.deal_id, deals.client_id, deals.lead_id, leads.parent_lead_id, leads.client_id, leads.email, clients.auth_user_id.
Description. Postgres does not auto-create indexes for foreign-key columns (only for the primary key on the referenced side). As row counts grow, every join, every WHERE deal_id = …, and every cascade check becomes a sequential scan.
Recommendation. Add B-tree indexes on every FK column and on lookup columns. Use CREATE INDEX CONCURRENTLY in production to avoid table locks. (Confirmation pending — Supabase dashboard access may reveal some of these already exist outside the public schema export.)

DB-005 — email_templates has both is_deleted and deleted columns High

Evidence: is_deleted boolean (nullable, no default) and deleted boolean NOT NULL DEFAULT false.
Description. Two columns for the same logical concept with different defaults and nullability. Application code likely reads one and writes the other in different places — a classic source of "I deleted it but it still shows up" bugs.
Recommendation. Pick one (deleted is better-defined). Backfill from is_deleted, update all code, then DROP COLUMN is_deleted.

DB-006 — tasks.completed and tasks.status duplicate the same state High

Description. Both columns track completion. They can disagree: completed=false, status='Completed' (or vice versa) is allowed at the DB level. Application logic must remember to update both, every time, in every code path — and it does not (cross-references GAP-007).
Recommendation. Keep status (richer enum). Drop completed. If client code still needs the boolean, expose it as a generated column: completed boolean GENERATED ALWAYS AS (status = 'Completed') STORED.

DB-007 — Three concurrent sources of truth for co-purchaser data High

Affected: leads.co_persons jsonb, leads.parent_lead_id (self-FK), deal_co_purchasers table.
Description. Co-purchaser/co-seller relationships are encoded in three places. The application code primarily uses parent_lead_id, but co_persons JSON and the deal_co_purchasers table also exist. Drift between them is inevitable and silent.
Recommendation. Pick the canonical model (parent_lead_id + lead rows). Migrate data out of the other two, then drop. Document the choice in CLAUDE.md.

DB-008 — Two tables for documents: deal_documents vs lead_corporate_docs High

Description. deal_documents stores documents against the deal; lead_corporate_docs stores documents against the lead. The APS / identification flows write to lead_corporate_docs. The purpose of deal_documents is unclear from the schema — if unused, it's dead; if used, the two tables are partial duplicates with different CHECK constraints and different status enums.
Recommendation. Audit usage; drop or merge.

DB-009 — leads.lead_type has no CHECK while task_templates.lead_type and stage_templates.lead_type do High

Description. Templates restrict lead_type ∈ {'Purchase','Sale','Refinance'}. The leads table itself allows any string. A lead with lead_type='Closing' (matching the service enum but not the template enum) will silently fail to match templates during conversion.
Recommendation. Add the same CHECK to leads.lead_type, or refactor to a single Postgres enum type (CREATE TYPE lead_type_enum AS ENUM ('Purchase','Sale','Refinance')) referenced from all three tables.

7.3 Medium

DB-010 — leads.price declared as text, not numeric Medium

Description. Prices stored as strings (likely because the intake form sends formatted values like "$450,000"). All arithmetic, ordering, and range filters require explicit casting. Compare with leads.selling_price numeric, deals.price numeric — the type inconsistency makes cross-table aggregation brittle.
Recommendation. Add a price_numeric numeric column, backfill via regex parse, switch reads to it, drop the text column.

DB-011 — lead_corporate_docs.doc_type CHECK has grown organically and is internally inconsistent Medium

Allowed values: 'Article of Incorporation', 'Corporation Profile', 'Special Shareholder Agreement', 'Directors Resolution', 'Other', 'aps', 'identification', 'home_insurance', 'mortgage', 'document', 'aps_purchase', 'aps_sale', 'retainer_agreement'.
Description. Mixed casing (Title Case vs snake_case), overlapping semantics (aps vs aps_purchase vs aps_sale), and a catch-all document bucket. Drives the auto-detection edge case in GAP-019.
Recommendation. Normalise to snake_case enum + the existing separate side column. Migrate data via a one-shot mapping. Replace CHECK with an enum type.

DB-012 — Six denormalised APS flags on leads Medium

Columns: aps_signed, aps_signed_purchase, aps_signed_sale, aps_uploaded, aps_uploaded_purchase, aps_uploaded_sale.
Description. Six booleans must be kept in sync with each other and with the underlying lead_corporate_docs rows. Update consistency is brittle and not enforced. Confirms application-side risk in GAP-019.
Recommendation. Derive these from lead_corporate_docs via a view or generated column. If they must remain materialised, add a trigger.

DB-013 — leads.parent_lead_id self-reference has no cycle prevention Medium

Description. A → B → A cycles are possible. Recursive code (family-deal traversal in familyDeals.ts, findFamilySharedTaskPeers) can stack-overflow or loop.
Recommendation. Add a trigger that walks parent_lead_id on INSERT/UPDATE and rejects cycles, or constrain to a 2-level hierarchy (apparently the business intent).

DB-014 — tasks.deal_id is nullable Medium

Description. A task with no deal is meaningless in this domain. The nullable FK admits orphans through any code path that forgets to set the column.
Recommendation. ALTER COLUMN deal_id SET NOT NULL after backfilling existing nulls.

DB-015 — Critical tables lack updated_at Medium

Affected: leads, clients, milestones, lead_corporate_docs, lead_identification_docs, retainer_signatures, deal_co_purchasers, deal_documents.
Description. Without updated_at, optimistic concurrency (GAP-001) cannot be implemented, audit reports cannot show "rows changed in the last 24 h," and debugging is harder.
Recommendation. Add updated_at timestamptz NOT NULL DEFAULT now() on every mutable table; maintain via a shared BEFORE UPDATE trigger.

DB-016 — No created_by / updated_by columns anywhere Medium

Description. Only deal_notes.created_by records an actor; no other table records who created or last touched a row. This compounds the audit-log gap in CMP-004: even with an audit_logs table, reconciling against per-row state is harder without these fields.
Recommendation. Add created_by uuid and updated_by uuid referencing auth.users(id) on every mutable table; populate from the request context once SEC-001 verifies the JWT.

DB-017 — task_responses.value has no type-check against field_type Medium

Description. A field declared field_type='number' can still store value='banana'. Type safety is purely advisory.
Recommendation. Either enforce at the application layer (Zod schema per field_type at write time) or add a CHECK using regex ((field_type <> 'number') OR (value ~ '^-?[0-9]+(\.[0-9]+)?$') with equivalent rules per type).

DB-018 — partners.agent_email not unique Medium

Description. Duplicate (brokerage, agent) entries are unconstrained.
Recommendation. Add UNIQUE (lower(brokerage_name), lower(agent_email)) via an expression index.

DB-019 — public.users (staff) has no auth_user_id link Medium

Description. clients.auth_user_id links to auth.users, but public.users (staff: Admin / Clerk / Lawyer) has no such link. deal_notes.created_by references public.users.id, not the auth user — so attributing notes to a signed-in admin requires a side lookup that may or may not exist. The staff auth model is unclear from the schema alone.
Recommendation. Add public.users.auth_user_id uuid UNIQUE REFERENCES auth.users(id); backfill from email match; make all created_by / updated_by columns reference auth.users(id) directly.

DB-020 — deals.status CHECK and application allow-list disagree Medium

Schema: CHECK (status IN ('Pending','Active','Inactive','Closed')). Application: ALLOWED_STATUSES = ['Active','Inactive','Closed'] (src/app/api/admin/deals/[id]/route.ts:313-317). deals_duplicate: accepts 'Cancelled', 'Urgent' too.
Description. Three drifting enums for the same concept. The DB accepts 'Pending', but the API rejects it — any row inserted with that status (e.g. via direct SQL or migration) becomes uneditable through the admin UI.
Recommendation. Define one Postgres enum type, reference it everywhere, generate TypeScript types from it.

8. Compliance & Data Protection

The platform operates in a Canadian real-estate context and handles PII including government identification documents. The applicable regimes are PIPEDA (personal information protection), CASL (commercial electronic messages), and provincial real-estate record-retention rules.

CMP-001 — Government-issued IDs stored on public-readable storage High

Location: src/app/api/admin/uploadblobstorage/route.ts:31-38 — also tracked as SEC-003.
PIPEDA Principle: Safeguards (Principle 7).
Recommendation. See SEC-003. Until a fix ships, stop uploading new ID documents to public Blob; route ID intake to an interim private path.

CMP-002 — Intake collects PII without explicit consent capture High

Location: src/components/Intake.tsx
PIPEDA Principle: Consent (Principle 3).
Recommendation. Add a final consent step before submission: a privacy-policy link, an affirmatively-ticked checkbox, and stored privacy_consent_at + privacy_consent_version per lead. The version field enables re-prompting when the policy changes.

CMP-003 — Identification documents forwarded to Google Gemini (US sub-processor) High

Location: src/app/api/admin/identify-document/route.ts:261-272
PIPEDA Principles: Identifying Purposes (2), Limiting Use/Disclosure (5), Openness (8).
Description. The full ID image is sent to Google Gemini for classification. Google is a US-based processor; without a documented DPA and explicit consumer disclosure, this is a PIPEDA gap.
Recommendation. (1) Disclose Gemini as a sub-processor in the public privacy policy. (2) Sign an enterprise DPA with Google Cloud, or migrate to Vertex AI in northamerica-northeast1 for Canadian data residency. (3) Crop documents to the boundary and strip EXIF before transmission.

CMP-004 — No audit log of sensitive access High

Description. PIPEDA's Accountability principle expects a demonstrable record of who accessed PII. The platform has no audit_logs table; impersonations, document accesses, ID classifications, and lead deletions are not recorded.
Recommendation. Introduce audit_logs(id, actor_user_id, action, resource_type, resource_id, before, after, ip, user_agent, created_at) and a recordAudit() helper invoked by impersonate, document download, lead/deal delete, ID classification, and bulk import.

CMP-005 — No data retention or right-to-be-forgotten flow Medium

Location: src/app/api/admin/leads/route.ts:40-45
Recommendation. Publish a retention schedule (e.g. closed deals + 7 years). Provide POST /api/admin/leads/[id]/erase that hard-deletes the lead, co-leads, documents, task responses, and Blob objects; record in audit_logs with a reason code.

CMP-006 — Transactional emails lack CASL-compliant unsubscribe Medium

Location: src/lib/sendWelcomeEmail.ts
Recommendation. Add {{ unsubscribe_link }} and the sender's physical address to every template. Implement /api/email/unsubscribe?token=… and a lead.email_opt_out flag; honour the flag in sendWelcomeEmail / sendAuthEmail.

CMP-007 — No HSTS / CSP / security headers Medium

Duplicates SEC-010; tracked here for compliance completeness.

CMP-008 — PII leakage via error responses and server logs Medium

Location: src/lib/sendWelcomeEmail.ts:346, src/lib/sendAuthEmail.ts, task-responses/route.ts:350-388
Recommendation. Return generic error codes/messages to the client; log full detail server-side only, with PII redaction in the logger.
